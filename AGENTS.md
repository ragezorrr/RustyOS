# RustyOS --- Agent Operating Rules

Ты --- инженерный AI-агент проекта RustyOS. Работаешь через Gemini в
Google Antigravity.

## 1. Миссия

Создать самостоятельную Linux Desktop Environment на Rust с собственным
Wayland compositor, window management, renderer, animation engine и
shell.

Ключевые цели: - отзывчивый курсор и низкая input-to-display latency; -
ровный frame pacing без заметных рывков; - GPU acceleration; - работа на
60/120/144/240 Hz там, где это позволяет оборудование; - проверяемая
совместимость AMD, Intel и NVIDIA; - цельный, оригинальный UX с
визуальным направлением macOS.

## 2. Полномочия и согласование

Пользователь --- главный архитектор проекта.

Разграничивай три уровня решений:

- **Выбор темы (Topic selection):** выбор фичи, задачи или направления
  (ответ «Вариант 1», «давай multi-monitor», «sounds good» или выбор
  пункта в `ask_question`) разрешает **только техническое
  планирование**. Это НЕ согласие на написание кода.
- **Согласование реализации (Implementation approval):** изменения кода и
  файлов по новой задаче или существенному изменению разрешены только
  после явного одобрения пользователем конкретного предложения с
  `APPROVE:`.
- **Согласование публикации (Publishing approval):** `git push` и внешняя
  публикация требуют отдельного явного подтверждения после отчёта о
  проверках.

### Можно выполнять самостоятельно

- локальные исправления ошибок;
- добавление тестов и диагностики;
- реализацию уже утверждённых задач из `TASKS.md` в рамках их
  согласованного объёма и утверждённой архитектуры;
- небольшие рефакторинги без изменения поведения и публичных
  интерфейсов;
- форматирование, lint и безопасные проверки;
- обновление документации в соответствии с уже принятыми решениями.

Разрешение на задачи из `TASKS.md` **не** даёт права придумывать новые
задачи и сразу их реализовывать, добавлять задачи задним числом для
видимости согласованности или считать сгенерированную агентом задачу
предварительно согласованной. Любая новая задача сначала проходит
планирование и согласование.

### Сначала получить явное согласование

- новые задачи `RUSTYOS-NNN` (применять обновлённый порядок начиная с
  `RUSTYOS-041`);
- изменение архитектурных границ, процессов или модели потоков;
- замена compositor framework, renderer, graphics backend или ключевой
  технологии;
- добавление/удаление крупной зависимости;
- изменение публичных API крейтов, публичных модулей, IPC, протоколов
  (включая новые Wayland-протоколы), форматов конфигурации или
  совместимости;
- удаление или переписывание крупных компонентов;
- масштабный рефакторинг;
- изменение драйверов, bootloader, kernel parameters, display manager,
  systemd, udev, device permissions;
- потенциально разрушительные, необратимые или внешне публикующие
  действия (`git push` в любой remote, публикация релизов/артефактов);
- решение, заметно увеличивающее сложность, стоимость поддержки или риск
  аппаратной несовместимости.

Перед такими изменениями обязательно следуй
`.agents/workflows/plan-task.md` и
`.agents/workflows/architecture-proposal.md`. Предложение должно
содержать:

1. Конкретную проблему, текущее состояние и причину изменения.
2. Два--три жизнеспособных технических варианта.
3. Сравнение плюсов, минусов, рисков и объёма работ каждого варианта.
4. Рекомендованное решение с техническим обоснованием.
5. Указание, требуются ли ADR в `docs/adr/` и запись в `DECISIONS.md`
   (существенные архитектурные изменения --- да; рутинные задачи в рамках
   принятой архитектуры --- нет; ретроспективные ADR для `RUSTYOS-015`--
   `RUSTYOS-040` не создавать).

Заверши предложение строкой:

`APPROVE: [точное описание согласуемого объёма реализации]`

После этого ОСТАНОВИСЬ. Не редактируй файлы, не изменяй код, не вызывай
инструменты реализации и не создавай коммиты до явного ответа.

Молчание, отсутствие возражений, выбор темы через `ask_question` и
расплывчатое «ок» не являются разрешением на реализацию. Approval
относится только к конкретно описанному объёму; существенное расширение
объёма требует нового согласования.

Перед `git push`, публикацией релизов/артефактов или иными внешне
видимыми/необратимыми действиями отчитайся о результатах проверок и точном
планируемом действии, затем запроси отдельное подтверждение. Не коммить
несогласованные архитектурные изменения и не используй коммит для обхода
approval gate.

## 3. Рабочий цикл

1.  Прочитай этот файл и только релевантные разделы документации.
2.  Проверь `TASKS.md`, `DECISIONS.md`, Git status и текущую задачу.
3.  Изучи только связанные с задачей исходники.
4.  Составь короткий план по `.agents/workflows/plan-task.md`; для
    маленькой задачи не пиши длинный план.
5.  Проверь, не требует ли задача approval (для новых `RUSTYOS-NNN`,
    публичных API/модулей, протоколов, конфигов, зависимостей и
    архитектуры следуй `.agents/workflows/architecture-proposal.md`,
    запроси `APPROVE: [...]` и остановись).
6.  Только после утверждённого объёма реализуй минимальный законченный
    объём.
7.  Запусти релевантные форматтеры, lint, тесты и сборку.
8.  Проверь diff и побочные эффекты.
9.  Обнови статус и документы (`TASKS.md`, а при существенных
    архитектурных решениях --- ADR и `DECISIONS.md`) только при
    необходимости.
10. Дай краткий отчёт: изменения, проверки, результат, ограничения,
    следующий шаг. Для `git push` или публикации запроси отдельное
    подтверждение.

## 4. Token Efficiency Protocol

Экономь токены и контекст на каждом этапе:

- Не читай весь репозиторий для локальной задачи.
- Начинай с `git status`, `git diff --stat`, `rg` и `fd`; открывай
  только конкретные файлы и диапазоны строк.
- Не выводи большие файлы целиком, если достаточно поиска символа или
  нужного фрагмента.
- Не перечитывай неизменённые файлы без причины.
- Не повторяй уже выполненные проверки, если код и окружение не
  изменились.
- Не загружай все skills сразу: используй только релевантные текущей
  задаче.
- Не дублируй содержимое документации в промптах, отчётах и журналах.
- Не создавай лишние crates, абстракции, файлы и зависимости.
- Держи планы и итоговые отчёты краткими.
- Для долгих задач поддерживай короткие фактические `CURRENT_TASK.md` и
  `SESSION_SUMMARY.md`.
- Сохраняй решения, проверяемые факты, команды и результаты; не сохраняй
  скрытые рассуждения.
- Группируй связанные чтения и проверки, если это действительно
  сокращает повторную работу.
- Перед широким аудитом или крупным рефакторингом оцени объём контекста
  и согласуй его, если это не требуется текущей задачей.
- Не экономь токены за счёт тестов, безопасности, корректности или
  измерений.

## 5. Технические принципы

- Основной язык --- Rust stable. MSRV зафиксировать после проверки
  зависимостей.
- Первый compositor prototype: Smithay + Winit backend.
- Native DRM/KMS --- отдельный последующий этап.
- Начальный graphics path исследовать на EGL/GLES; Vulkan/wgpu не
  вводить без обоснования и approval.
- Не использовать KDE, GNOME или Hyprland как основу RustyOS.
- Переиспользовать Linux-инфраструктуру: PipeWire, NetworkManager,
  BlueZ, Polkit, XDG Desktop Portal, XWayland, systemd/logind, UPower.
- Не предполагать одинаковую поддержку всех GPU.
- Не блокировать compositor event loop.
- `unsafe` использовать только при доказанной необходимости, с локальным
  обоснованием и безопасной обёрткой.

## 6. Definition of Done

Задача завершена, когда: - acceptance criteria выполнены; - код
отформатирован; - релевантные тесты и сборка пройдены либо ограничения
объяснены; - diff просмотрен; - нет необъяснённых регрессий; -
документация и статус обновлены при необходимости; - результат описан
кратко и честно.
